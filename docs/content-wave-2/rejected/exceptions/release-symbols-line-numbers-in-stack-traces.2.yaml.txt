    explanation: |
      Имена файлов и номера строк не хранятся в IL-коде сборки. Их хранят символы - PDB: соответствие
      исходного кода и скомпилированного файла. В .NET 10 среда выполнения и отладчики читают символы из
      переносимого PDB, который лежит рядом со сборкой или встроен в неё (`DebugType` равный `embedded`
      записывает отладочную информацию прямо в `.dll`). Документация отмечает, что только старые среды, такие
      как .NET Framework 4.7.1 и более ранние, не умеют печатать стеки вызовов с номерами строк из переносимых
      PDB. Если PDB нет, кадр выводится без `in ...:line N`. Частая причина - этап Dockerfile или скрипт
      упаковки, который копирует только `*.dll`, либо сборка с `DebugType` равным `none`.

      Варианты a и c - две альтернативы, а не два обязательных шага: для проекта выбирают одну из них.
      Отдельный `.pdb` не увеличивает сборку, но его легко потерять при копировании. Встроенный PDB
      невозможно потерять, но он увеличивает размер `.dll`. Если в процесс выпуска добавляется проверка
      наличия символов, она должна принимать любой из двух вариантов.

      Для дампов важно другое: дамп разбирают позже и на другой машине. Символы привязаны к конкретной
      сборке через идентификатор PDB, записанный в сборку (его описывает спецификация формата Portable PDB),
      поэтому нужны символы той самой сборки. Их сохраняют для каждого выпуска на сервере символов или в
      артефактах сборки. Source Link добавляет в сборку и PDB метаданные системы контроля версий: соответствие
      исходных файлов их адресам на конкретном коммите, и отладчик загружает исходники ровно той версии,
      которая работала. Руководство по Source Link также советует детерминированные сборки: одинаковые входные
      данные дают побайтно одинаковый результат, и можно проверить, что двоичный файл собран из указанного
      исходного кода.

    title: How do you bring file names and line numbers back into the stack traces of a .NET 10 production service?
    prompt: |
      A team ships a .NET 10 service as a Docker image. In production logs the stack traces look like
      `at OrderService.Process(Order order)`, without `in ...:line 42`, and a dump taken a month ago opens in
      the debugger without source code. You own the build and release process.

      Select all practices that bring file names and line numbers back into stack traces or keep dumps
      debuggable later.
    hint: Where is the mapping from IL code to source lines stored, and how does the debugger make sure that file belongs to this exact assembly?
    options:
      a: "Ship the `.pdb` files produced by the build next to their assemblies: do not strip `*.pdb` in the Dockerfile or packaging script, and do not build with `<DebugType>none</DebugType>`."
      b: "Build production in the Debug configuration or turn optimization off: a Release build cannot produce line numbers in stack traces."
      c: "Build with `<DebugType>embedded</DebugType>`: the portable PDB is embedded in the `.dll`, so it cannot be lost on the way to production, and no separate `.pdb` is needed."
      d: "Archive the symbols of every release build (a symbol server or build artifacts) and enable Source Link, so that a dump taken months later loads matching symbols and the debugger fetches the source of the exact commit."
      e: "Keeping the source code is enough: to analyze an old dump, rebuild the head of the release branch and point the debugger at the new `.pdb`."
      f: "Enabling Source Link is enough: the runtime then takes line numbers from the repository, and `.pdb` files are no longer needed in production."
    optionExplanations:
      b: "Line numbers come from the PDB, and a PDB is produced for a Release build too: to get none, you have to set `DebugType` to `none` explicitly. Optimization only affects precision: the JIT may inline a method so its frame disappears from the stack, and a line is sometimes approximate. There is no need to give up optimization in production for this."
      e: "Symbols are tied to a specific build: the PDB identity is recorded in the assembly, and the debugger needs the symbol file with exactly that identity. The branch head is different code and a different build, so its PDB does not match the old dump. You need the symbols of the exact build that ran in production."
      f: "Source Link does not replace the PDB: it stores in the PDB a mapping from source file paths to the URLs of those files at a specific commit, so the debugger can download them. The mapping from IL offsets to lines lives in the PDB itself, and without it neither the runtime nor the debugger gets line numbers."
    answer: "Ship the `.pdb` files next to the assemblies or embed the PDB with `<DebugType>embedded</DebugType>` (either of the two works), and archive the symbols of every release together with Source Link."
    explanation: |
      File names and line numbers are not stored in the IL of an assembly. Symbols - the PDB - store them: a
      mapping between the source code and the compiled binary. In .NET 10 the runtime and debuggers read symbols
      from a portable PDB that sits next to the assembly or is embedded in it (`DebugType` set to `embedded`
      writes the debugging information into the `.dll` itself). The documentation notes that only older
      environments, such as .NET Framework 4.7.1 and earlier, cannot print stack traces with line numbers from
      portable PDBs. Without a PDB the frame is printed without `in ...:line N`. A common cause is a Dockerfile
      stage or packaging script that copies only `*.dll`, or a build with `DebugType` set to `none`.

      Options a and c are two alternatives, not two mandatory steps: a project picks one of them. A separate
      `.pdb` does not make the assembly larger, but it is easy to lose while copying. An embedded PDB cannot
      be lost, but it makes the `.dll` larger. If the release process gets a check for symbols, it must
      accept either form.

      Dumps need something else: a dump is analyzed later and on another machine. Symbols are tied to a
      specific build through the PDB identity recorded in the assembly (the Portable PDB format specification
      describes it), so you need the symbols of that exact build. They are kept for every release on a symbol
      server or in build artifacts. Source Link adds source control metadata to the assembly and the PDB: a
      mapping from source files to their URLs at a specific commit, and the debugger downloads the source of
      exactly the version that ran. The Source Link guidance also recommends deterministic builds: identical
      inputs give a byte-for-byte identical binary, so you can verify that a binary was built from the stated
      source.
