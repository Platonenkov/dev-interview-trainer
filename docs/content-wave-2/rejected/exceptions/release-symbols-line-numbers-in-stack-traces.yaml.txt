    explanation: |
      Номера строк и имена файлов не хранятся в IL сборки. Компилятор записывает их в файл символов (PDB):
      там лежит соответствие смещений IL строкам исходника. Документация о символах прямо связывает их с
      печатью трассировок стека с номерами строк: без подходящего PDB остаются только имена методов. Среда
      выполнения ищет переносимый PDB рядом со сборкой (файл с тем же именем и расширением `.pdb`) или внутри
      самой сборки, если PDB встроен. PDB должен быть от той же сборки: сборка и PDB содержат общий
      идентификатор, и символы от другой сборки не подходят.

      Отсюда три решения:

      - **Наличие символов проверяется автоматически.** Символы обычно теряются не у компилятора, а при доставке:
        Dockerfile копирует только `*.dll`, конвейер удаляет `*.pdb`, или кто-то задал `DebugType` равным `none`.
        Гейт в CI превращает это из случайности в нарушение, которое не пропустит релиз.
      - **PDB встроен в сборку.** С `DebugType` `embedded` отдельного файла `.pdb` нет, символы едут вместе
        с DLL, и потерять их по пути нельзя. Цена - немного больший размер сборки.
      - **Символы архивируются, включён Source Link.** Дамп разбирают позже и на другой машине, поэтому PDB
        каждого релиза хранят не меньше срока поддержки версии, а у хранилища есть владелец и политика хранения.
        Source Link записывает в сборку и пакет сведения о репозитории и коммите, а в PDB - карту путей файлов на
        адреса в репозитории, и отладчик сам загружает исходники нужного коммита.

      Руководство по Source Link также советует включать детерминированные сборки: они позволяют проверить, что
      двоичный файл собран из указанного исходника. В проектах .NET детерминированная компиляция включена по
      умолчанию, но совпадение результата требует тех же входных данных, включая версию компилятора, поэтому
      это не замена архиву символов.

      Для лида это прежде всего решение о процессе: символы - часть релизного артефакта, их наличие проверяется
      автоматически, а хранение символов входит в политику хранения релизов. Поведение описано для .NET 10.

    title: Why do production stack traces have no line numbers, and how should you set up build and release so they do?
    prompt: |
      Your team owns a .NET 10 service. In production logs, exception stack traces contain method names but no
      file names and no line numbers. Dumps taken during past incidents cannot be matched to the source code of
      the version that was running at the time.

      Select all build and release process decisions that fix this and keep dumps debuggable later.
    hint: Where is the mapping from IL code to source lines stored, and what happens to that file on its way from the build to production and to whoever analyzes the dump six months later?
    options:
      a: "Add a gate to the release pipeline: publishing or building the image fails if the service assemblies have no `.pdb` next to them or the project sets `DebugType` to `none`. Typical causes of lost symbols are a Dockerfile step that copies only `*.dll` files, or deleting `*.pdb` to save space."
      b: "Deploy the Debug configuration to production, because the Release configuration removes line information from the assembly."
      c: "Set `<DebugType>embedded</DebugType>`: the portable PDB is stored inside the assembly itself, so it cannot be lost or mismatched separately from the DLL."
      d: "Log `ex.ToString()` instead of `ex.Message`: file names and line numbers are then read from the IL metadata of the assembly, and no PDB is needed."
      e: "Archive the PDBs of every release build on a symbol server or in build artifacts, kept for at least the support window of the version, assign an owner to that store, and enable Source Link, so a dump taken months later opens with matching symbols and the sources of the exact commit."
      f: "Rely on Source Link alone and strip PDBs from the image: the Source Link metadata in the assembly is enough for the runtime to restore line numbers in stack traces."
      g: "To save storage, keep symbols only for the latest release: dumps of older versions can be analyzed with the PDBs of a newer build, since the code changes little between releases."
    optionExplanations:
      b: "In SDK-style projects the Release configuration also produces a portable PDB by default: to suppress it you must explicitly set `DebugType` to `none`. Release differs by having optimizations on, not by lacking symbols. Debug in production hurts performance and does not help if the PDB still never reaches the server."
      d: "`ToString()` does add the stack trace, but IL metadata has no file names or line numbers: they exist only in the PDB. Without symbols the trace still has no lines."
      f: "Line numbers come from the PDB, which maps IL offsets to source lines. Source Link writes repository and commit information into the assembly and the package, while the map from file paths to repository URLs also lives in the PDB. Without the PDB there are neither line numbers nor that map. Besides, Source Link is for a debugger downloading sources, not for the runtime building a stack trace."
      g: "A PDB fits only the assembly it was produced with: they share an identifier, and IL offsets and lines differ in another version of the code, so the symbols of a newer build do not fit an old dump. A deterministic build lets you rebuild the same commit, but only with the same compiler version and the same referenced assemblies, so it does not replace a symbol archive."
    answer: "A pipeline gate that blocks a release without `.pdb` files; an embedded PDB with `DebugType` `embedded`; an archive of every release's symbols with a retention policy and an owner, plus Source Link."
    explanation: |
      Line numbers and file names are not stored in the assembly's IL. The compiler writes them to a symbol file
      (PDB), which maps IL offsets to source lines. The symbols documentation directly ties them to printing stack
      traces with line numbers: without a matching PDB only method names remain. The runtime looks for a portable
      PDB next to the assembly (a file with the same name and the `.pdb` extension) or inside the assembly itself
      if the PDB is embedded. The PDB must come from the same build: the assembly and the PDB carry a shared
      identifier, and symbols from a different build do not fit.

      That leads to three decisions:

      - **The presence of symbols is checked automatically.** Symbols are usually lost not by the compiler but in
        delivery: a Dockerfile copies only `*.dll`, a pipeline deletes `*.pdb`, or someone set `DebugType` to
        `none`. A CI gate turns this from an accident into a violation that blocks the release.
      - **The PDB is embedded in the assembly.** With `DebugType` `embedded` there is no separate `.pdb` file,
        the symbols travel with the DLL and cannot be lost on the way. The cost is a somewhat larger assembly.
      - **Symbols are archived and Source Link is on.** A dump is analyzed later and on another machine, so the
        PDBs of every release are kept for at least the support window of that version, and the store has an
        owner and a retention policy. Source Link writes repository and commit information into the assembly and
        the package, and the map from file paths to repository URLs into the PDB, so the debugger downloads the
        sources of the right commit itself.

      The Source Link guidance also recommends deterministic builds: they let you verify that a binary was built
      from the specified source. Deterministic compilation is on by default in .NET projects, but an identical
      result needs identical inputs, including the compiler version, so it is not a substitute for a symbol
      archive.

      For a lead this is above all a process decision: symbols are part of the release artifact, their presence
      is checked automatically, and keeping symbols is part of the release retention policy. The behaviour is
      described for .NET 10.
