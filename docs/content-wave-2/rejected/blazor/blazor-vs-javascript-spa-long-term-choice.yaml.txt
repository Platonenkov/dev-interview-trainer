  ru:
    title: "Как выбрать между Blazor и JavaScript SPA-фреймворком для продукта, который будет жить много лет?"
    prompt: |
      Компания с сильной командой .NET начинает продукт, который должен развиваться и поддерживаться много лет.
      В продукте есть публичные страницы, личный кабинет с формами и таблицами и администрирование. Одна часть
      архитекторов предлагает Blazor (Blazor Web App в .NET 10), другая - SPA на JavaScript/TypeScript-фреймворке
      поверх HTTP API на ASP.NET Core.

      Как вы примете это решение: какие критерии взвесите, на каком уровне будете решать и как снизите риск
      ошибиться на годы вперёд?
    hint: |
      Одинаковы ли требования к первой загрузке, интерактивности и SEO у разных частей продукта, и какие
      свойства команды и рынка меняются медленнее, чем фреймворки?
    answer: |
      1. **Решать по поверхностям продукта, а не для всей компании.** Разделить продукт на части с разными
         требованиями: публичные и контентные страницы (SEO, быстрая первая отрисовка на мобильных), личный
         кабинет и администрирование (формы, таблицы, бизнес-правила), сильно интерактивный или офлайн-клиент,
         виджеты для встраивания в чужие сайты. Для каждой части решение может быть своим.
      2. **Что даёт Blazor.** Один язык и один набор инструментов; модели, правила валидации и контракты API
         общие для сервера и клиента в виде .NET-библиотек; команда .NET-разработчиков делает функцию целиком.
         В Blazor Web App (начиная с .NET 8, в том числе в .NET 10) контентные страницы отдаются статической
         отрисовкой на сервере без клиентской среды выполнения, а интерактивность включается на уровне страницы
         или компонента.
      3. **Чем Blazor платит.**
         - `InteractiveWebAssembly`: до первого взаимодействия браузер загружает среду выполнения .NET и сборки
           приложения. Тримминг, сжатие и кэширование уменьшают объём, но первое посещение обычно тяжелее, чем
           бандл типичной JavaScript SPA, и это нужно измерить на целевых устройствах. AOT-компиляция ускоряет
           выполнение ценой ещё большего размера загрузки.
         - `InteractiveServer`: загрузки нет, но каждое событие интерфейса - это сетевой запрос туда и обратно,
           нужно постоянное соединение, а сервер держит память на каждую цепь (circuit).
         - Экосистема: готовых UI-компонентов заметно меньше, чем в npm. Остаются коммерческие библиотеки
           компонентов или обёртки над JavaScript-библиотеками через interop, и каждую обёртку придётся
           сопровождать.
         - Найм: фронтенд-специалистов с опытом JavaScript/TypeScript на рынке больше, чем людей с опытом
           Blazor; зато .NET-разработчиков в компании уже много. Это надо сопоставить с реальным составом команды
           и планами найма.
      4. **Снизить долгосрочный риск архитектурой.** Устареть могут оба варианта: у JavaScript-фреймворков
         мажорные версии и смена сборочного инструментария, Blazor движется вместе с выпусками .NET (мажорная
         версия каждый ноябрь, LTS-версия раз в два года) и зависит от инвестиций Microsoft. Поэтому
         бизнес-логика и валидация живут вне UI-компонентов, а сервер отдаёт версионируемый HTTP API, пригодный
         для любого клиента: интерфейс одной поверхности можно переписать, не трогая бэкенд. Технологии могут
         сосуществовать: Blazor вызывает JavaScript через interop, а компоненты Razor можно встроить в
         JavaScript-приложение как корневые компоненты или пользовательские элементы (custom elements).
      5. **Решать на измерениях и фиксировать решение.** Прототип самых сложных экранов, замеры первой загрузки на
         целевых устройствах и сетях, задержки взаимодействия и скорости разработки. Решение записать в ADR с
         условиями пересмотра: смена аудитории, состава команды, требований к офлайну.

      Типичный итог: личный кабинет и администрирование на Blazor, публичные страницы на статической серверной
      отрисовке, а отдельный сложный потребительский клиент - там, где это оправдано измерениями и командой.
    explanation: |
      Вопрос не про то, какой фреймворк «лучше», а про то, какие издержки продукт будет платить годами. Выгода от
      общего C#-кода велика, когда на клиенте много логики: валидация, расчёты, сложные формы. Если интерфейс -
      тонкий слой над API, выгода мала, а общие DTO для TypeScript можно генерировать из описания OpenAPI.

      Цена WebAssembly - размер и время первой загрузки, и бьёт она сильнее всего по анонимным пользователям на
      мобильных сетях, то есть по публичным страницам. Для внутреннего кабинета, куда сотрудник заходит каждый
      день и файлы уже в кэше, та же цена почти незаметна. `InteractiveServer` снимает загрузку, но переносит
      цену на задержку сети и память сервера. Поэтому один критерий весит по-разному для разных поверхностей, и
      общее решение для всей компании почти всегда оказывается неверным хотя бы для одной из них.

      Экосистема и найм меняются медленнее фреймворков, поэтому для решения на годы они важнее модных
      возможностей. Главная защита от ошибки - не угадать фреймворк, а сделать его заменяемым: чистая граница API
      и логика вне UI позволяют переписать одну поверхность, а не весь продукт. Описанные режимы отрисовки
      относятся к Blazor Web App начиная с .NET 8 и верны для .NET 10.

  en:
    title: "How do you choose between Blazor and a JavaScript SPA framework for a product that will live for many years?"
    prompt: |
      A company with a strong .NET team starts a product that must be developed and maintained for many years.
      The product has public pages, a customer account area with forms and grids, and an admin area. Some
      architects propose Blazor (a Blazor Web App on .NET 10), others propose an SPA on a JavaScript/TypeScript
      framework on top of an ASP.NET Core HTTP API.

      How do you make this decision: which criteria do you weigh, at what level do you decide, and how do you
      reduce the risk of being wrong for years ahead?
    hint: |
      Do different parts of the product have the same needs for first load, interactivity and SEO, and which
      properties of the team and the market change more slowly than frameworks do?
    answer: |
      1. **Decide per product surface, not for the whole company.** Split the product into parts with different
         needs: public and content pages (SEO, fast first paint on mobile), the account and admin areas (forms,
         grids, business rules), a highly interactive or offline client, widgets embedded in other sites. Each
         part may get its own decision.
      2. **What Blazor gives.** One language and one toolchain; models, validation rules and API contracts shared
         by server and client as .NET libraries; a team of .NET developers delivers a feature end to end. In a
         Blazor Web App (since .NET 8, including .NET 10) content pages are served with static server-side
         rendering and no client runtime, and interactivity is enabled per page or per component.
      3. **What Blazor costs.**
         - `InteractiveWebAssembly`: before the first interaction the browser downloads the .NET runtime and the
           app assemblies. Trimming, compression and caching reduce the size, but the first visit is usually
           heavier than the bundle of a typical JavaScript SPA, and this has to be measured on target devices.
           AOT compilation speeds up execution at the price of an even larger download.
         - `InteractiveServer`: no download, but every UI event is a network round trip, the app needs a
           persistent connection, and the server keeps memory for every circuit.
         - Ecosystem: there are far fewer ready UI components than on npm. What remains are commercial component
           libraries or wrappers over JavaScript libraries through interop, and every wrapper must be maintained.
         - Hiring: the market has more frontend specialists with JavaScript/TypeScript experience than people with
           Blazor experience; on the other hand the company already has many .NET developers. Weigh this against
           the real team and the hiring plan.
      4. **Reduce long-term risk with architecture.** Both options can age: JavaScript frameworks have major
         versions and build toolchain churn, Blazor moves with the .NET release cadence (a major version every
         November, an LTS version every two years) and depends on Microsoft's investment. So business logic and
         validation live outside UI components, and the server exposes a versioned HTTP API that any client can
         use: the UI of one surface can be rewritten without touching the backend. The technologies can coexist:
         Blazor calls JavaScript through interop, and Razor components can be hosted inside a JavaScript app as
         root components or custom elements.
      5. **Decide on measurements and record the decision.** Prototype the hardest screens, measure first load on
         target devices and networks, interaction latency and development speed. Record the decision in an ADR
         with triggers for revisiting it: a change of audience, team composition or offline requirements.

      A typical result: the account and admin areas in Blazor, public pages with static server-side rendering,
      and a separate complex consumer client only where measurements and the team justify it.
    explanation: |
      The question is not which framework is "better" but which costs the product will pay for years. The benefit
      of shared C# code is large when the client holds a lot of logic: validation, calculations, complex forms. If
      the UI is a thin layer over an API, the benefit is small, and shared DTOs for TypeScript can be generated
      from an OpenAPI description.

      The price of WebAssembly is the size and time of the first download, and it hits hardest anonymous users on
      mobile networks, that is, public pages. For an internal area that an employee opens every day with the files
      already cached, the same price is barely noticeable. `InteractiveServer` removes the download but moves the
      cost to network latency and server memory. So one criterion weighs differently for different surfaces, and a
      single company-wide decision is almost always wrong for at least one of them.

      The ecosystem and the hiring market change more slowly than frameworks, so for a decision that lasts years
      they matter more than fashionable features. The main protection against a mistake is not guessing the right
      framework but making it replaceable: a clean API boundary and logic outside the UI let you rewrite one
      surface instead of the whole product. The render modes described here apply to Blazor Web Apps since .NET 8
      and hold for .NET 10.
