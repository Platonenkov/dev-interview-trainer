    explanation: |
      Если конструктор производного класса не содержит инициализатора `: base(...)`, компилятор неявно вызывает

      не используется, поэтому внутреннее поле сообщения у `Exception` остаётся пустым.

      Свойство `Exception.Message` в таком случае не возвращает `null`, а подставляет текст по умолчанию вида
      `Exception of type '<имя типа>' was thrown.` Тип объявлен в глобальном пространстве имён, поэтому в тексте
      стоит просто `OrderException`. Сообщение вызывающего кода потеряно, и в логе остаётся бесполезная строка.

      Строки 14 и 22 не дефектны: исключение создаётся с правильным сообщением, а `OrderId` сохраняется верно.
      Исправление - добавить в объявление конструктора `: base(message)`. Документация рекомендует, чтобы
      собственное исключение передавало сообщение (и при необходимости `innerException`) в конструктор
      `Exception`, а не хранило его в своём поле или переопределяло `Message`: тогда `Message`, `ToString()` и
      логирование работают как у встроенных исключений.

  en:
    title: Find the line that makes a custom exception lose its message
    prompt: |
      The `PlaceOrder` method throws a custom `OrderException` with an order number and the message
      `Quantity must be positive`. The caller catches it and prints the order number and `Message`.
      The expected result is `Order 42: Quantity must be positive`, but the program prints:

      ```text
      Order 42: Exception of type 'OrderException' was thrown.
      ```

      Click the line that contains the defect.
    hint: Which base class constructor is called when a derived class constructor does not name one explicitly?
    answer: Line 20, the constructor `OrderException(int orderId, string message)` does not pass the message to the base class with `: base(message)`.
    explanation: |
      When a derived class constructor has no `: base(...)` initializer, the compiler implicitly calls the
      parameterless base class constructor, here `Exception()`. The `message` parameter is accepted but never
      used, so the internal message field of `Exception` stays empty.

      In that case the `Exception.Message` property does not return `null`; it supplies a default text of the form
      `Exception of type '<type name>' was thrown.` The type is declared in the global namespace, so the text
      shows just `OrderException`. The caller's message is lost, and the log keeps a useless line.

      Lines 14 and 22 are not defects: the exception is created with the right message, and `OrderId` is stored
      correctly. The fix is to add `: base(message)` to the constructor declaration. The documentation
      recommends that a custom exception pass the message (and `innerException` when needed) to the `Exception`
      constructor rather than keep it in its own field or override `Message`: then `Message`, `ToString()` and
      logging work as they do for built-in exceptions.
