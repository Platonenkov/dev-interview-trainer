      c: "The inner `catch` clauses are not checked for the new exception at all: it leaves the inner `try` statement right away. So `catch2` is not printed."
      d: "The inner `try` statement is nested in the outer one, and the inner `catch` clause sits inside the outer `try` block. The outer `catch (ArgumentException)` catches the new exception."
      e: "`InvalidOperationException` and `ArgumentException` are not related by inheritance, so neither clause makes the other unreachable (no CS0160), and `throw` inside `catch` is allowed."
    answer: "catch1 outer"
    explanation: |
      The `catch` clauses of a `try` statement handle only exceptions thrown while its `try` block runs. Here
      `InvalidOperationException` is thrown in the `try` block, the handler search finds the first matching
      clause, `catch (InvalidOperationException)`, and it prints `catch1 `.

      That clause then throws a new `ArgumentException`. It was raised in a `catch` block, not in the `try`
      block, so the sibling `catch` clauses of the same statement are not checked, even though the type matches.
      The exception leaves the inner `try` statement as a whole (a `finally` there would run) and looks for a
      handler in the enclosing code. The whole inner statement is inside the `try` block of the outer statement,
      so the outer `catch (ArgumentException)` runs and prints `outer`.

      The practical takeaway: if a handler translates one exception into another, the result must be caught one
      level up, not by a sibling `catch`. And when you translate, pass the original exception as
      `innerException`, otherwise the root cause is lost.
