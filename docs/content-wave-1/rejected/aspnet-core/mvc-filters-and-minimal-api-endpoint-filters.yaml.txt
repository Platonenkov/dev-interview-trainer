    explanation: |
      Фильтры MVC (авторизации, ресурсов, действий, исключений, результатов) выполняет механизм вызова действий MVC.
      Он работает только для конечных точек MVC: для действий контроллеров и для Razor Pages в части тех типов
      фильтров, которые они поддерживают (фильтры действий в Razor Pages не поддерживаются, вместо них есть фильтры
      страниц). Конечная точка minimal API обрабатывается без этого механизма, поэтому ни глобальные фильтры MVC,
      ни атрибуты фильтров MVC на лямбде к ней не применяются.

      Для minimal API есть свой механизм - фильтры конечных точек, появившиеся в .NET 7. Фильтр реализует
      `IEndpointFilter` или передаётся делегатом `(context, next) => ...` в `AddEndpointFilter`. Он оборачивает
      вызов обработчика: видит привязанные аргументы, может изменить результат или прервать обработку, не вызвав
      `next`. Фильтры не выполняются при ошибках чтения тела запроса (например, некорректный JSON); при других
      ошибках привязки фильтр выполняется, но аргументы могут быть привязаны лишь частично, поэтому сначала стоит
      проверить код состояния ответа. `AddEndpointFilter` работает и на группе из `MapGroup` - это ближайший
      аналог глобальных фильтров для набора конечных точек.

      Для логики, общей для контроллеров и minimal API, есть два пути: middleware, который выполняется для любой
      конечной точки, или тот же фильтр конечной точки, подключённый к контроллерам через
      `MapControllers().AddEndpointFilter(...)`. Поведение описано для .NET 10.

  en:
    title: How do you apply filter logic to minimal API endpoints?
    prompt: |
      An ASP.NET Core application (.NET 10) has controllers with MVC filters and new minimal API endpoints.
      Select all true statements about adding filter logic to minimal API endpoints.
    hint: Which component invokes MVC filters, and does it take part in handling a request to an endpoint declared with `MapGet`?
    options:
      a: "Global MVC filters added with `AddControllers(options => options.Filters.Add<T>())` do not run for minimal API endpoints."
      b: "A minimal API endpoint filter implements `IEndpointFilter` (or is given as a delegate) and is attached with `AddEndpointFilter`."
      c: "An endpoint filter can be added to a group created with `MapGroup`, and then it applies to every endpoint in the group."
      d: "An attribute derived from `ActionFilterAttribute` placed on a `MapGet` handler lambda runs just as it does on a controller action."
      e: "An endpoint filter runs before parameter binding, so it cannot read the handler arguments."
    optionExplanations:
      d: |
        MVC filters, including attributes based on `ActionFilterAttribute`, are executed only by the MVC action
        invoker, which handles controller actions. A request to a minimal API endpoint does not go through it, so
        `OnActionExecuting` and the other methods of the attribute are never called.
      e: |
        An endpoint filter runs after parameter binding: the arguments are available through
        `EndpointFilterInvocationContext.Arguments` and `GetArgument<T>(index)`. That is why a filter can validate
        the arguments and return a result, such as a validation error, without calling `next`.
    answer: "a, b and c are true."
    explanation: |
      MVC filters (authorization, resource, action, exception, result) are executed by the MVC action invoker.
      It runs only for MVC endpoints: controller actions, and Razor Pages for the filter types they support
      (action filters are not supported in Razor Pages, which use page filters instead). A minimal API endpoint is
      handled without the MVC action invoker, so neither global MVC filters nor MVC filter attributes on the
      lambda apply to it.

      Minimal APIs have their own mechanism, endpoint filters, introduced in .NET 7. A filter implements
      `IEndpointFilter` or is passed as a `(context, next) => ...` delegate to `AddEndpointFilter`. It wraps the
      handler call: it sees the bound arguments, can change the result, or can stop processing by not calling
      `next`. Endpoint filters do not run for body-reading failures (such as malformed JSON); after other binding
      failures a filter still runs, but the arguments may be only partially bound, so it should check the
      response status code first. `AddEndpointFilter` also works on a `MapGroup` group, which is the closest
      analogue of global filters for a set of endpoints.

      For logic shared by controllers and minimal APIs there are two options: middleware, which runs for any
      endpoint, or the same endpoint filter attached to controllers with `MapControllers().AddEndpointFilter(...)`.
      The behaviour described is for .NET 10.
